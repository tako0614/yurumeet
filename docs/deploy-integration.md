# Yurumeet GA integration fixture

The isolated integration entrypoint is `bun run deploy -- yurumeet-integration --environment=integration --phase=<phase>`. It is bound to `https://ga-meet-20261012.yurucommu.com`, resource prefix `yurumeet-ga-20261012-0938`, and the immutable `v0.2.0` Worker asset pinned in `release.lock.json` (`3b952ec6c0ee048bfd303344f8053c21c01ae8bdca780db57c908c6e171d1bd0`). It has no path to the production `yurumeet` Worker or its data.

The normal new-resource path runs `preflight`, `resources`, `fresh-schema`, `activate`, then `domain`. For the exact existing 32-migration D1, use `recover-prefix32` in place of `fresh-schema` and only after its separate evidence gate; it intentionally does not call the create-only preflight or adopt another resource. `fresh-schema` stays fresh-only, and `recover-prefix32` is not a general resume mode. The optional `probe-case-parser` and `probe-case-parser-comparison` investigations are separate from this readiness sequence. Preflight checks the exact existing account and `yurucommu.com` zone, then paginates the D1, R2, KV, Queue, Worker, and custom-domain inventories. Parser-probe D1 inventories request the unfiltered D1 list with `page=1&per_page=10000` and require one complete page (`page=1`, `count=rows.length=total_count`, and `total_count<=10000`); incomplete or contradictory responses stop before creation. Worker-domain filters require the requested page and consistent `count`/`total_count`; an empty filtered response is valid with `total_count:0` and `per_page:0` or the requested page size. Any collision, denied read, or incomplete inventory stops the sequence. Public DNS results do not establish whether a record is absent: zone DNS reads are denied, and wildcard responses can return 522. The final domain phase relies on the exact Cloudflare custom-domain changeset and explicit no-overwrite flags.

`resources` copies the root OpenTofu module into the private operator directory and accepts only creation of a fresh D1 database, R2 bucket, KV namespace, delivery and DLQ Queues, and the root module's random identifier. The Worker stays disabled. The D1 resource explicitly sets `read_replication.mode = "disabled"` using the optional object in the pinned [Cloudflare provider v5.19.1 D1 schema](https://github.com/cloudflare/terraform-provider-cloudflare/blob/v5.19.1/docs/resources/d1_database.md). This matches the observed disabled setting and avoids a disabled-to-null update in later activation plans; a fresh exact plan must still confirm no D1 update before apply. State and plans stay outside Git worktrees in the operator's 0700 directory and are 0600 or stricter. Raw tool/API diagnostics stay in unique 0600 files inside its private diagnostics directory. Existing resources are never imported, adopted, replaced, or destroyed.

`fresh-schema` reads that private state's exact D1 id and calls `scripts/deploy-integration-schema.mjs`. The helper confirms a fresh database and absent target Worker, probes rollback with the same REST batch transport used for migrations, then applies the exact published Core 4.2.0 migration set with one REST batch per migration and checks the shared `yurucommu_migrations` ledger and schema. The live REST execution uses the same exact pinned 0034 `CASE`-expression projection exercised by the isolated full-35 qualification; all other pinned migration bytes remain unchanged. `activate` verifies all 35 expected migration names before creating only the Worker, queue consumers, and hourly cron. Supply distinct 64-hex encryption key and session salt plus a nonblank integration password credential through ephemeral `TF_VAR_encryption_key`, `TF_VAR_session_hash_salt`, and `TF_VAR_auth_password_hash` environment variables. These credentials configure this test fixture only and do not change account or membership policy. Do not put secrets in the target file or source. OpenTofu state remains sensitive private operator material.

`recover-prefix32` is a one-target forward repair for the exact existing integration D1. It reads the database UUID/name from the private OpenTofu state and requires the target Worker to remain absent. Before writing, it builds a prefix-32 reference from the pinned Core 4.2.0 runner and unmodified SQL, then compares the remote schema objects, every table count, exact 32-row ledger IDs/names, `sqlite_sequence`, FTS seed bytes, and foreign-key check. Any mismatch refuses before a schema write. The recovery path validates but does not send the runner's ledger-initialization SQL; the runner must skip exactly migrations 0001–0033 and request only 0034–0036. Each migration uses one existing REST batch, with an exact growing 33/34/35 ledger readback before proceeding. The final full schema, object definitions, counts, ledger, sequence, seed rows, and foreign-key state must match a separately built Core-35 reference whose only execution projection is the already-qualified exact 0034 `CASE` expression. This is not a generic resume path and does not repair another database or an arbitrary ledger prefix. The ordered reads cannot exclude an out-of-band writer. A pre-write mismatch is `PREFIX32_PREFLIGHT_REFUSED`; once any suffix batch is attempted, every uncertain write or later readback is `POST_SCHEMA_INDETERMINATE`. Stop without retry, cleanup, or replay and use authoritative read-only reconciliation before any further action. Execution remains gated on independent source review, the separate isolated full-35 qualification, and its one-use operator evidence.

`probe-case-parser` is a separate diagnostic phase for Cloudflare D1 trigger handling. It refuses any preexisting exact target name and creates three new standalone D1 databases (`...-parser-bare`, `...-parser-parenthesized`, and `...-parser-values`) with no Worker, bindings, or domains. Each receives one seven-statement REST batch: one trigger variant, a probe ledger marker, an insert that exercises the trigger, and a late duplicate-key failure. It records created database identities, request hashes, and private 0600 raw-response logs, including the complete before/after `sqlite_master` query responses and their SHA-256 values; the query results must be unchanged. An exact `incomplete input: SQLITE_ERROR` response to the bare `CASE ... END;` case is reported as `INCOMPLETE_INPUT_OBSERVED`; it does not prove which statement failed or establish the cause of Core migration 0034's failure. Any uncertain transport or schema residue stops remaining cases as `POST_PARSER_PROBE_INDETERMINATE`; it does not retry or delete these disposable databases.

`probe-case-parser-comparison` is a separately invoked continuation for the two remaining variants only. It creates only new `...-parser-parenthesized` and `...-parser-values` databases; it never reuses, recreates, or otherwise adopts the already observed bare fixture. Before each one-time create, it rechecks the complete bounded D1 inventory and confirms the target Worker remains absent. Each new database gets the same single seven-statement batch and full-schema readback. If a target name exists, a response is incomplete, the Worker appears, or any result is uncertain, it stops without a retry, cleanup, or third database. Both diagnostic phases are outside readiness/GA qualification and do not alter the integration database, Core migrations, or Worker identity.

`native-full35` is a separate one-use diagnostic phase. It first reads the exact account and `yurucommu.com` zone, confirms the target Worker is absent, then requires one complete unfiltered D1 inventory (`page=1&per_page=10000`, with `count`, returned rows, and `total_count` equal and no more than 10000). It creates only `yurumeet-ga-20261012-0938-native-full35`, outside OpenTofu state, and writes a private 0600 create receipt before exact UUID/name readback. It never adopts an existing database, retries a create or batch, deletes the fixture, or activates a Worker/domain. After the existing fresh-schema and same-transport rollback guards, it applies the pinned Core 4.2.0 35-migration sequence. Only the exact `SELECT CASE … END;` expression inside `0034_staged_media_retention.sql`'s `media_staged_process_input` trigger is projected to `SELECT (CASE … END);`; the original migration digest, all other SQL bytes, published migration map, runner, and `yurucommu_migrations` ledger are unchanged. The helper privately retains successful REST response evidence and requires ordered ledger IDs/names, complete schema object and trigger equality against an offline pinned Core-35 SQLite reference, no foreign-key violations, and the exact three unstarted media backfill rows. The diagnostic tests this narrowly projected execution shape; it does not establish the exact cause of prior 0034 failures or qualify the integration Worker, user experience, or GA. Any uncertain create or schema result is `POST_NATIVE_FULL35_INDETERMINATE`; preserve the D1 and reconcile by read-only inspection.

`domain` requires the exact activated state and no existing Worker custom domain for the hostname or target service. It requires a changeset with exactly one addition and empty `updated`, `removed`, and `conflicting` arrays (missing arrays are refused), repeats the domain inventory, then writes with `override_existing_origin:false` and `override_existing_dns_record:false`. It reads back the hostname, service, and zone and checks the public origin. Cloudflare creates DNS and TLS as part of a Worker custom domain. A failed or uncertain write requires authoritative readback before another invocation; Wrangler's noninteractive custom-domain path is unsuitable because its override flags permit takeover.

An `APPLIED` phase result proves the exact OpenTofu plan and private state address set only. A successful domain readback and HTTP 2xx do not prove the Worker's complete bindings or authenticated product behavior. Before describing the live fixture as qualified or GA, separately read back the exact Worker artifact and binding closure from Cloudflare and run the scoped authenticated user smoke against this origin.

Set `YURUMEET_INTEGRATION_TARGET` to an absolute, link-free 0600 JSON file under a 0700 directory outside all Git worktrees and the source Git common directory. It must contain exactly `accountId`, `zoneId`, `origin`, `prefix`, `releaseTag`, `artifactSha256`, `sourceCommit`, and `stateDir`. The target binds the exact source commit and artifact pin; `stateDir` is an existing 0700 child directory. Pass the existing Cloudflare OAuth token as ephemeral `CLOUDFLARE_API_TOKEN`; never place credentials in command arguments, logs, target files, or source.

After OpenTofu apply begins, any apply or state/mode-readback failure is reported as `POST_APPLY_INDETERMINATE`. A fresh-schema executor error is reported as `POST_SCHEMA_INDETERMINATE`; a domain error from the no-overwrite PUT through provider and public-origin readback is `POST_DOMAIN_INDETERMINATE`. Stop and inspect authoritative Cloudflare state and private OpenTofu state before another invocation. This adapter has no destroy or automatic rollback path. It does not qualify production lifecycle, production data/schema, new billing or auth grants, or public service GA.

The portable bundle's deliberate D1-safe 0003 override is validated through the owning bundle generator; this fresh native D1 lane executes the exact published Core SQL files, and validates all immutable inputs before its first probe write.

The fresh-schema executor validates the pinned Core runner's complete script, then uses the installed Wrangler SQL splitter to preserve each compound trigger as one statement. A lexical whitespace shim handles its `(CASE` and `END)` boundary defects without changing quoted tokens, comments or the pinned SQL files. It sends exactly one REST `{batch:[{sql}, …]}` request per migration, with ledger initialization first and the matching migration mark last. For migration 0034 it applies only the exact pinned `SELECT CASE … END;` to `SELECT (CASE … END);` statement projection in every live execution path: fresh-schema, native-full35, and recover-prefix32. The migration digest, runner, ledger, and every other Core SQL byte stay unchanged. It requires the exact result count and successful, error-free results for every statement. Before any real migration, the same batch transport creates probe tables, a nested-CASE trigger and a synthetic ledger mark, then deliberately fails a late duplicate-key insert. Readback must find no probe tables, trigger or ledger; a parser failure, residue or uncertain response stops without cleanup or retry. Portable SQLite tests prove request shape and refusal behavior; real D1 trigger parsing, batch rollback and all 35 migrations still require isolated live qualification. A database with earlier migrations remains non-fresh for `fresh-schema`; that phase provides no resume path.

Activation rechecks the complete Worker inventory before planning and immediately before apply. The Cloudflare Worker upload is a PUT, so these reads cannot atomically exclude a concurrent creator with the exact same reserved fixture name; a create-only private plan is not remote conditional-create proof. A collision is refused and any uncertain upload is reconciled without replay.

A newly created remote D1 contains the reserved `_cf_KV` table. The empty-schema guard ignores only exact `_cf_KV` and `_cf_METADATA` objects whose type is `table`, alongside SQLite system objects. Application tables, `_cf_` lookalike names, views and triggers still stop the run before the rollback probe or any migration. This matches the reserved-table behavior in [Cloudflare D1 import/export documentation](https://developers.cloudflare.com/d1/best-practices/import-export-data/); it never reads or deletes reserved-table contents.
