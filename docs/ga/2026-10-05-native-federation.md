# Yurumeet native federation smoke — 2026-10-05

The existing release artifact smoke exercises one Worker. The federation smoke runs two instances of the same freshly built `dist/takos-worker.js` with separate disposable D1, KV, R2 and delivery queues. `bun run check` invokes it after the artifact smoke without rebuilding between them. The fixture checks the Yurumeet discovery identity while retaining the shared `yurucommu` family-engine token.

Each instance creates an owner and session through the real mobile password API. **One API-created owner per fixture is test setup, not a Yurumeet account policy.** A follows private B, B sees and accepts the request, and both Workers' relationship data and owner-facing APIs must agree. B sends a followers-only post and a direct message to A. The smoke checks signed inbox delivery, delivery jobs, remote actor cache separation, local and remote object projections, authenticated reads, and anonymous denials. The recipient activity uses a receiver-local ID while retaining the sender's wire ID in its raw envelope.

Exact peer HTTPS origins and public DNS answers are virtualized by in-workerd routers. The routers preserve URL, Host, body, digest and signature; unrecognized outbound requests are denied. The explicit `--deny-peer-key-fetch` control blocks an unsigned peer-key request and must fail the journey. The supervisor bounds the child process, and a passing JSON record is emitted only after native runtime disposal and temporary state removal. A failed journey or cleanup emits `FAILED` JSON to stderr and exits nonzero.

This is same-product, local-native evidence for Yurumeet built bytes, including native queue delivery. It does not establish public DNS/TLS, live federation or live Queue/Cron delivery, real issuer integration, transport retry/DLQ/redrive, existing operator-data update/restore, cross-product federation, or Core publication/adoption. Those require their own evidence. This change does not alter Core packages, pins, schema, authority, or deployment state.

## Genuine delayed endpoint recovery

The default router refuses the first genuine signed followers-addressed Create with HTTP 503 before forwarding it to the receiver. Native D1 must show the same application job in `retry_wait`, one failed attempt, a closed circuit with one failure and no recipient Note. The published Core producer schedules the actual native Queue wakeup using its first 48–72 second jittered backoff. The fixture does not rewrite clocks or ledger timestamps and does not fabricate batches. It allows one second of schedule precision around the backoff; actual arrival must be no more than two seconds early or 15 seconds late against the persisted due time.

The same job, activity, object and recipient then return signed inbox 202, with delivered state, cleared error/processing marker, reset circuit and exactly one Note. Existing DM/read/privacy checks continue. Successful Core delivery retains `next_attempt_at`; clearing that field is not required or claimed. The strict `--deny-endpoint-retry` control blocks the next real retry for that exact activity/object and observes attempts2, `retry_wait`, circuit2 and no Note before failing. It cannot be combined with `--deny-peer-key-fetch`. Failure JSON stays on stderr, stdout remains empty, and cleanup gates every result. The wrapper bounds the native process at 300 seconds.

## Digest refusal and correctly signed actor mismatch

Before forwarding the first actual Queue-produced A-to-B Follow, the router sends a separate valid-JSON clone differing by one activity-ID hex nibble, with the same byte length and unchanged URL/Host/Date/Signature/Digest/Content-Length. Actual B must return401 `Signature verification failed` with zero inbound activities, dispatch claims, inbox entries, follow edges and remote objects. Read-only observer aliases refer to B's existing disposable native D1; they are test fixture capabilities, not product bindings.

A separate clone changes only the claimed actor to a clearly different path on A's same origin. The router reads the actual API-created A owner key from A's existing disposable native D1, computes fresh RSA-SHA256 signature, Digest and UTF-8 Content-Length using the genuine sender key ID, and self-verifies the exact outgoing Request. Actual B must return401 `Actor mismatch`, after cryptographic verification and before ledger claims; generic signature failure does not qualify actor binding. Global inbound counters plus genuine and claimed-actor Follow edges must remain zero before/after. Actor cache may populate during key resolution, so the proof does not claim that all database state remains unchanged.

After both probes, the original Queue Request is forwarded unchanged:202, one processed receiver-local activity retaining original raw wire ID, one claim and one pending edge. No claimed actor activity/claim/edge or altered-ID record may appear. The manifest records only safe IDs, body hashes, counts and verification booleans; no keys, signatures, bodies or cookies are logged. Both probes run in the default and endpoint-denial journeys; key-denial disables them and retains the original key-fetch failure oracle.

The owning Yurumeet gate and CI must qualify its own source and freshly built `takos-worker.js`; another product's success cannot substitute. These tests add no Yurumeet account policy or Core pins/schema/runtime features. Correctly signed foreign-wire-ID anti-poisoning, SSRF negatives, public DNS/TLS, real federation and operator qualification remain separate.
