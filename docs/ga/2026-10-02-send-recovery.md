# Conversation-scoped outgoing recovery

Task GA-20261002-meet-send-recovery. Yurumeet dedicated worktree only, stacked after qualified PR #34 (`20944f8`). Parent owns ChatProvider/ChatPane, draft integration, recovery coordinator and qualification. Journal worker owns journal and focused tests; browser worker owns operator fixtures; independent reviewer owns read-only review. Protect original message-search changes, Yurucommu #61, Core/control and other worktrees. No production deploy, resource/permission/billing changes, publication, merge, real-data deletion or live D1 migrations apply.

The old reviewed Worker loses a held send after switching to another talk and aborting before backend admission. Local Chrome reproduces exactly one POST, zero D1 Notes, no automatic retry, and no failed bubble or composer payload on return. This evidence uses immutable #34 bytes, not the changing candidate source. Earlier operator setup failures are preserved separately.

Outgoing intents are saved and read back in tab-local sessionStorage before composer clearing or POST. Identity includes resolved server origin, signed-in actor AP ID, contact type/AP ID and UUID. Only immutable text and uploaded media references are stored, never preview/blob URLs, file bytes or credentials. Denied, partial or invalid storage prevents sending and leaves the composer intact. New text drafts use the same identity boundary; legacy contact-only drafts are neither imported nor deleted because their author is unknown. Yurumeet's ownership model is unchanged; Yurucommu's single-owner rule is not extended here.

Consequently, a text draft stored by an older client remains in storage but is not automatically displayed after this update. Recovery/import of those drafts requires an explicit author-aware policy. This change also requires working sessionStorage to begin a send; clients that deny it keep their input and receive an actionable warning.

Latest keyed state is merged after asynchronous history/poll responses and survives talk switches. Same-tab reload turns pending into unconfirmed, never automatic POST. Unknown outcomes retain the existing duplicate warning and explicit retry. A valid server ACK saves its actual ID before journal removal and deduplicates only by that ID. Storage failure leaves cautious recovery on reload. Discard hides only a failed local intent after verified journal removal; it never deletes canonical Notes or media. Forward API calls use the same coordinator, although the current client has no forwarding UI.

Qualification requires focused failure/race tests, actual Chrome scenarios preserving the prior 58 checks, explicit formatting, read-only full `bun run check`, exact committed-tree CI, independent review, original/Yuru protection readback and a bound operator receipt. Source, local synthetic runtime, CI and live/public install evidence remain distinct. No green or GA claim is made by this implementation plan.

This journal is tab-local reload recovery, not crash-proof, cross-device or cross-tab atomic delivery. Shared per-intent idempotency, Follow hydration and reference-safe unused uploads remain Core/API proposals. Public v0.1.2/Core3.2.0/19 migrations (including divergent same-name 0019), existing-data upgrade/delete/restore policy, published app+Provider+Host install/update/rollback/lifecycle/monitor, deployed federation/Queue/Cron, real Takos issuer/token refresh and materializer custody remain separate dependencies.
